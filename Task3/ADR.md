### <a name="_qmphm5d6rvi3"></a>**Решение**

Диаграмма контекста в [icepannel](https://s.icepanel.io/eNwnlIk1evcv5k/tEjR) или локально в [файле](./C4_context.png)
Диаграмм контейнеров в [icepannel](https://s.icepanel.io/eNwnlIk1evcv5k/3ZlR) или локально в [файле](./C4_container.png)

Добавлено два микросервиса: для открытия депозитов и для обработки ставок. Сервис депозитов обрабатывает запросы открытия депозитов из интернет-банка,
отправляет коды подтверждения через СМС-шлюз, т.к. прямого взаимодействия с АБС лучше избегать, т.к. у АБС очень медленное API, то само
открытие депозита вынесено в воркер сервиса депозитов, данный воркер вытаскивает из БД подтверждённые запросы и взаимодействует с АБС. После
открытия депозита в АБС, как и раньше, пользователю отправляется СМС с уведомлением.

Сервис обработки ставок позволяет загружать в него данные из XLS-файлов, получать информацию по загруженным ставкам, вносить точечные изменения.
Для клиентских запросов через интернет-банк или сайт предлагается использовать кэш, т.к. скорей всего данные будут редко изменяться. 
Доступ к сервису из внутреннего контура будет производиться через админку, которая интегрирована с keycloack для использования RBAC-разграничений.
Подробнее данная система будет описана в 4 задании.

В качестве баз данных можно выбрать MS SQL, т.к. у команды уже есть опыт её использования. Бэк можно пилить на ASP.NET Core также из-за имеющейся у команды 
интернет-банка экспертизы в C# и ASP.NET.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
Прямая интеграция интернет-банка с АБС. Это упрощает архитектуру, но усложняет приложение интернет-банка, а также увеличивает нагрузку на АБС.

Использование очереди сообщений Kafka для интеграции сервиса депозитов и АБС, но текущая версия платформы интернет-банка несовместима с Kafka и 
отсутствует экспертиза у команды, что увеличит время разработки и может ухудшить качество продукта.

**Недостатки, ограничения, риски**

Нужно прокачивать команду DevOps-ов, настраивать процесс CI/CD, но в долгосрочной перспективе данный недостаток превратиться в плюс.
Для масштабирования микросервисов нужны свободные железные ресурсы, но на начальном этапе можно использовать развёртывание у какого-нибудь облачного
провайдера. Тут нужно считать. Главное, чтобы расходы на облочного провайдера не разорили банк.
